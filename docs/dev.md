# Developer Guide

## Setup and commands

The project is managed with [uv](https://docs.astral.sh/uv/): `uv sync` creates `.venv` with the package installed editable and the `dev` dependency group, pinned by `uv.lock`. The editable install also puts the project root on the path, so `ingest/` and `tests/` import in development although the wheel ships only `src/localis`. Dev commands are [poethepoet](https://poethepoet.natn.io/) tasks in `pyproject.toml`'s `[tool.poe.tasks]`, run as `poe <task>` in the activated venv (`uv run poe <task>` outside it), with any extra arguments passed through: `poe ingest` (the data pipeline, see Pipeline below), `poe analysis` (`--data-only`, `--staging`, `--check`, `--notes`), `poe test`, `poe watch` and `poe watch-fast` (pytest-watch, the latter skipping slow tests), `poe typecheck`, and `poe sync-main` (fast-forwards the checked-out branch to `origin/main` and pushes it). `poe` alone lists them. They are dev-only and never installed with the package. To release, bump with `uv version --bump <part>` and merge a PR from `dev` into `main`; the release workflow builds with `uv build` and publishes. Then run `poe sync-main` on `dev`: the merge commit leaves `dev` behind `main`, and `main`'s ruleset only merges a PR that's up to date with it.

## resolve-subdivisions (Claude Skill)

`ingest_subdivisions()` builds its subdivision set from GeoNames (`admin1CodesASCII.txt`, `admin2Codes.txt`) and merges in ISO 3166-2 as the source of truth, using fuzzy matching (`ingest/subdivisions/scripts/automerge/`) to pair each ISO subdivision with its GeoNames counterpart. Fuzzy matching alone can't confidently resolve every pair: GeoNames and ISO frequently disagree on transliteration, use different eras' names for the same region, or one side uses a colloquial or local form the other doesn't. Others have no GeoNames counterpart and are added as new entries.

Whatever's left unmatched after fuzzy merging is an "orphan". Forcing a low-confidence match would silently corrupt the dataset, so orphans are instead handed off for resolution with real-world geographic knowledge using the resolve-subdivisions skill, which is almost entirely automated.

### Pipeline integration

`ingest/subdivisions/outputs/resolution_map.json` is the single source of truth for every ISO subdivision's resolution, not just the ones that needed human help. It's loaded once into a `ResolutionMap` (`ingest/subdivisions/utils/resolution_map.py`) at the start of `ingest_subdivisions()` and threaded through every stage:

1. `apply_skill_decisions()` (`ingest/subdivisions/scripts/resolve_subdivisions.py`) applies every entry in `resolution_map.skill_decisions` directly, before fuzzy matching ever runs, so a human-verified decision can never lose its target to a fresh auto-merge.
2. `try_merge()` (`ingest/subdivisions/scripts/automerge/try_merge.py`) auto-merges whatever's left and writes the result straight into `resolution_map.automerge`: a successful match (with its score margin over threshold) into `resolutions`, an unmatched one into `orphans.no_candidates`/`no_matches`/`ambiguity` depending on why, and a winning match less than `MARGIN_FLOOR` (5) points over its threshold into `orphans.low_margin` with its candidate, for the skill to confirm or reject. ISO subdivisions of a country with no GeoNames subdivisions at all are added as-is and listed in `geonames_absent` instead of orphaned, since there is nothing for the skill to decide. This recomputes fully on every run, so an algorithm improvement reaches every automerge result without any manual cache-invalidation step to forget.
3. `resolution_map.save()` persists the whole file immediately after merging, regardless of whether orphans remain, so the skill always has the current state to work from. `check_iso_coverage()` then raises if any ISO code in the release neither ships nor is an orphan, a code a merge step dropped without recording, which neither the orphan gate nor the reconcile gate could see. Then a hard gate: if any orphans remain in any of the seven buckets (the four from `try_merge()`; `wikidata_conflict`, from `flag_wikidata_conflicts()`, which re-sends any skill decision that disagrees with a valid Wikidata mapping it didn't record in `wikidata_seen`; `wikidata_changed`, from `apply_wikidata_matches()`, which holds back a mapping that differs from the code's prior resolution (an unresolved `wikidata_changed` orphan's previous target, else the committed crosswalk's valid mapping, else last run's automerge match); and `grouping_twin`, from `flag_grouping_twin_merges()`, which re-sends an automerge result that went into a non-administrative grouping's GeoNames twin because `apply_non_administrative()` couldn't identify the twin before automerge ran), `ingest_subdivisions()` logs the exact counts and calls `sys.exit(10)` before `dump_registry()` or the handoff to `ingest_cities()` ever runs, refusing to ship an incomplete dataset. The gate runs only after merging, on freshly recomputed orphans, never at the start of a run: a rerun is how a pipeline fix reaches orphans left by an earlier run, and skill decisions already made persist in `skill_decisions` across reruns. A clean run (no orphans) proceeds to stage subdivisions and `docs/unmerged_subdivisions.md` and hand its geocode map to the cities stage. An orphan stop exits before promotion, so the shipped data is untouched, and leaves the run's staging in place: the skill reads the staged countries (`load_countries()`), since the shipped ones may be a different build from the one that produced the orphans.

### Resolving Orphans

The skill (`.claude/skills/resolve-subdivisions/SKILL.md`) is a Claude Code skill backed by a local MCP server (`.claude/skills/resolve-subdivisions/scripts/server.py`, can be launched manually via `uv run python ...`). It drains `resolution_map.json`'s `automerge.orphans` lists one entry at a time.

Run the skill with Opus 5.5 or a stronger model. Earlier runs with Sonnet 5 produced enough wrong merges and unjustified adds to leave dirty data and duplicate records, while an audit of 107 Opus 5.5 decisions found none.

**Tools**

- **`next_orphan()`**: Returns the next orphan and a batch of candidates drawn from every GeoNames subdivision in its country, regardless of level, since ISO and GeoNames can file the same place at different levels. Candidates are ranked by the same `score_candidates()`/type-family-filtered scoring auto-merge uses, with same-level candidates first on ties, and paginated: a "top tier" first batch (~10% of the pool, ~75% of matches are found here), then fixed 200-candidate chunks. Records already claimed by another ISO code are included but marked `CLAIMED BY <iso_code>`, so a wrong earlier claim is visible; `merge` rejects them. Records the type-family rule would disqualify are included too (`score_candidates(..., include_type_disqualified=True)`), marked as a type mismatch, since that rule misfires on cases like city-states. `ambiguity` and `low_margin` orphans get the specific GeoNames records `try_merge` flagged as their first batch (contested targets, or the near-threshold pick), and fall through to the full pool, those records excluded, only if the agent rejects them. Candidates come back as a list ordered best first, not an ID-keyed dict, since serialization sorts dict keys and loses the ranking. Repeated `next_orphan()` calls page through the same orphan until its candidates run out. Each session has a context budget of about 150k estimated tokens (`TOKEN_BUDGET` in `server.py`): the server counts its own output and adds fixed allowances per orphan and per web search, since it can't see the agent's reasoning or search results. Once the budget is reached, the next `next_orphan()` call between orphans asks the user to `/clear`. The budget exists mainly for cost, since every call resends the whole context.
- **`merge(candidate_geonames_id)`**: Resolves the current orphan into a selected, unclaimed GeoNames candidate by its `geonames_id`.
- **`add(reason)`**: Adds the orphan as its own new entry, for subdivisions that are real but have no GeoNames counterpart. `reason` must say concretely why GeoNames lacks the place.
- **`review(reason)`**: An escalation valve for unresolvable cases. The agent reports its findings to the user in the session and asks for the decision, then the reason, with `AskUserQuestion`, and the server holds `reason` until the user's decision comes back through `merge` or `add`, which stores it as the decision's `escalation`. The candidate list isn't persisted, since it can be regenerated from the data. The orphan must be resolved with `merge` or `add` before the session can continue.

Both `merge` and `add` write a `SkillDecision` into `resolution_map.skill_decisions` (`id`, `reason`, `decided_by`, which is `"human"` when the orphan was escalated with `review` first and `"agent"` otherwise, and `escalation`, the agent's findings for a human decision) and remove the orphan from whichever `automerge.orphans` bucket it was in. Both require a `reason`: for `merge`, one sentence on why the candidate is the same place.

The server caches the resolution map, the GeoNames subdivisions with their claims, the ISO subdivisions, the staged countries and the crosswalk for as long as its process runs. Claude Code starts one server per session, launched with `.venv/bin/python` directly (`.mcp.json`), and `/clear` doesn't restart it, so the server records `resolution_map.json`'s modification time whenever it loads or saves the map. A different time means a fresh ingest or another session's decision wrote the file: `next_orphan()` then clears every cache and restarts the current orphan, and `merge`/`add` refuse until it has, so a session never writes over newer state.

**Decision funnel** (`SKILL.md` Steps 1–4): try a high-confidence `merge` against the current candidate batch → if none fit, page to the next batch and repeat → once `next_orphan()` returns no candidates at all, websearch the orphan first, always, before deciding anything (merge if the search reveals a confident match, `add` if it confirms the orphan is real but has no GeoNames counterpart) → if the search still doesn't resolve it, `review()` and defer to human intervention. The old path that allowed a self-certified `add` without searching first was removed after it produced reckless, unverified adds; websearch is now mandatory, not a last resort.

## Data Sourcing

Countries pull ISO 3166-1 codes and names from Debian's iso-codes project, country metadata from GeoNames' `countryInfo.txt`, and additional aliases from a live Wikidata query (`ingest/countries/scripts/wikidata_countries.py`: each ISO alpha-2 item's English label, alternative labels and short names, and the same for each item with an ISO 3166-3 alpha-4 code, for historic entries). Subdivisions pull ISO 3166-2 codes and names from the same iso-codes project (`iso_3166-2.json`) and admin boundaries from GeoNames' `admin1CodesASCII.txt` and `admin2Codes.txt`, with aliases from GeoNames' alternate names. Macroregions pull CLDR's territory containment and English territory names from the `unicode-org/cldr-json` repository (`ingest/macroregions/`), and each country's placement in them is set during the countries stage (`ingest/countries/scripts/place_macroregions.py`). Currencies pull ISO 4217 codes and names from iso-codes (`iso_4217.json`, `ingest/currencies/`), and each country's currencies are set during the countries stage from CLDR's `currencyData.json` (`ingest/countries/scripts/place_currencies.py`): the entries in use on the run date that aren't marked `_tender: false`, in CLDR's order, for current countries only, with a warning for any dated to start or end later. Scripts pull ISO 15924 codes and names from iso-codes (`iso_15924.json`) and CLDR's English script names (`scripts.json`) as aliases (`ingest/scripts/`, whose build scripts sit in `ingest/scripts/scripts/` like every domain's). Languages pull ISO 639-3 from iso-codes (`iso_639-3.json`), CLDR's English language names (`languages.json`) as aliases and CLDR's `languageData.json` for each language's scripts (`ingest/languages/`), and each country's languages are set during the countries stage from CLDR's `territoryInfo.json` (`ingest/countries/scripts/place_languages.py`): one entry per tag with an official status, keeping the tag's script. Cities pull from GeoNames' `cities500.txt`, GeoNames' own pre-filtered export (population ≥ 500, or a seat of an administrative division regardless of population), so `ingest/cities/scripts/load_cities.py` no longer applies its own feature-code or population filtering on top, GeoNames already made that call, and re-filtering on population would wrongly drop the low/no-population admin seats `cities500` specifically includes on purpose.

### Pipeline

`poe ingest` runs the pipeline (`ingest/__main__.py`, `run_pipeline()`). It first fetches the shared sources (`alternateNamesV2.txt` and CLDR's `territoryInfo.json`, read by countries and subdivisions) once, recorded in `ingest/shared/inputs/shared.manifest.json`. Every stage then builds from its inputs on every run, in dependency order (macroregions, currencies, scripts, languages, countries, subdivisions, cities), and receives the models of the stages it links to from earlier in the same run, so a dataset is never built against another run's ids and nothing is read back from shipped data. A stage only downloads an input that is missing locally, whose ETag differs from the one last recorded for it, or whose contents no longer match that record's SHA-256; deleting an input forces its re-download. The last record is the fetched record (below) when a run since the last promotion fetched the source, else the committed manifest's entry, so a rerun after a failed or orphan-stopped run doesn't download again what that run already did. Repeated runs on the same inputs produce identical files, which the CI version bump relies on.

Stages dump to `ingest/staging/` (ignored): each registry's files under `staging/data/<registry>/`, and every other file promoted with the data under `staging/files/` at its repo path (`stage_text()`): the source manifests, the committed Wikidata results, `docs/unmerged_subdivisions.md`, `ingest/cities/outputs/ingest_stats.json` and the change reports. Once every stage has dumped, `run_pipeline()` marks staging complete, runs the reconcile gate (`python -m tests.analysis --staging`, which checks that `data_stats`' counts for the staged build reconcile and writes nothing), stages the change reports and promotes (`ingest/utils/staging.py`): each staged registry directory replaces its `src/localis/data/` counterpart, the staged files move to their repo paths, and staging is cleared. It then regenerates `data_stats.json` and the docs' stat markers from the promoted build (`python -m tests.analysis --data-only`), so they never describe a build that didn't ship. Staging is otherwise cleared only at the start of the next run, so a failed or orphan-stopped run's build stays readable. That reset first merges the run's staged manifests into `staging/fetched/`, the fetched record of what each stage's `inputs/` holds, which promotion clears along with the rest of staging once the committed manifests catch up. Written on every run, success or not: each stage's log, with an `ERROR` line for the exception that stopped it (`ingest_log.stage()`), `resolution_map.json`, and `ingest/pipeline.log` (`pipeline_log.run()`), which lists the run's steps with both analysis runs' output and ends with exactly one result line: succeeded with the build promoted, stopped on orphans, or failed in a named step, saying whether the build was promoted.

The change report (`ingest/utils/change_report.py`) compares the staged build with the shipped one through two separate sets of registries rooted at each. Each stage's `ingest/<stage>/outputs/change_report.md` opens with a counts table (records before and after, added, removed, changed), then lists every record of its registry added, removed and changed by `key`, with the fields each changed record differs in, uncapped. Nested records compare by key, so a renamed country doesn't count as a change to every city in it, but the facts a relationship carries (a `CountryLanguage`'s status and share) do. The ingest workflow gathers each report's counts row into a summary table, each row linking to the stage's full report at that run's commit, and puts it in the ingest PR's body and a comment on each run; the full lists stay in the committed files, since a month of city changes outgrows GitHub's 65,536-character limit on PR bodies and comments.

Analysis reads the shipped data by default. With `--staging` it only checks that the complete staged build's data stats reconcile, never reading a mix of staged and shipped data: `data_stats.use_staging()` overrides `Registry._data_path` on analysis's side, so the runtime itself only ever reads its packaged data, and points the stats at the staged data directory, whose files the size and filter-index stats read, and at the staged copies of `ingest_stats.json` and the Wikidata crosswalk.

A stage's directories and files derive from its name (`Stage` in `ingest/utils/paths.py`: `inputs`, `outputs`, `manifest`, `log_file`), so adding a stage means the stage itself, a `Stage` constant, its call and `pipeline_log.step()` in `run_pipeline()`, its registry in `change_report._registries()` if it builds one, and a `.gitignore` exception for its manifest. The orchestration's logic (`fetch()`'s download decision, `reset_staging()`, `promote()`, the change report's comparison and both logs) is covered by `test_fetch.py`, `test_staging.py`, `test_change_report.py` and `test_ingest_logs.py` under `tests/unit/`, against files under a temporary directory with the network requests stubbed.

### Automated ingest pipeline (CI)

The monthly refresh described above is implemented in `.github/workflows/ingest.yaml`, which runs end-to-end against a long-lived `ingest` branch, on a monthly cron (`0 6 1 * *`) and on every push to `ingest`.

Each run merges the latest `dev` into `ingest`, then runs `poe ingest`. If any subdivision orphans remain, `ingest_subdivisions()`'s hard gate (see Pipeline integration above) saves `resolution_map.json` and calls `sys.exit(10)` before promotion. The workflow then commits only the orphan queue and the logs to `ingest` ("chore: ingest found N orphans awaiting resolution"), pushes, and fails the job, so the exact orphans the run found are on record in the branch rather than lost with the runner. Nothing was promoted, so the shipped data, manifests and committed Wikidata results are as they were, and nothing downstream (version bump, dataset commit, PR) runs. The push uses the workflow's own token, so it doesn't re-trigger the workflow.

Resolving orphans is a local procedure:

1. Pull `ingest`.
2. `poe ingest`, which builds the whole pipeline into staging, reproduces the orphan queue, and stops with exit 10, leaving staging for the skill. Compare its orphans with the committed queue; a difference means a source (usually Wikidata) changed in between.
3. Run the resolve-subdivisions skill until no orphans remain.
4. `poe ingest`, which now runs clean, passes the reconcile gate and promotes the build.
5. Commit and push to `ingest`, which re-triggers this workflow through its push trigger.

After a clean run, the workflow stages whatever changed. If `src/localis/data` (the published dataset) changed, it bumps the **patch** version with `uv version --bump patch` before committing. A data refresh doesn't touch the public API, so minor is reserved for genuine backward-compatible additions; conflating the two would mean a consumer reading `1.4.0 → 1.5.0` couldn't tell "just fresher data" from "there's a new method worth checking out." Freshness is still visible, just through each run's change reports in the ingest PR rather than the version number itself. Bookkeeping files (the per-domain `*.manifest.json`, `resolution_map.json`, the logs and the change reports) can change independently of the dataset output and still get committed on a run where the dataset itself didn't move. Everything staged is committed and pushed back to `ingest`, then a single, persistent `ingest` → `dev` pull request is created (ready for review, not draft, since reaching this point already guarantees a clean, orphan-free run) or, if it already exists, updated: its body carries the latest run's change report summary and each run comments its own (see Pipeline above). Each report compares a run's build with the one before it on `ingest`, not the PR's whole diff against `dev`, so a run that changes nothing after one that did reports zeros and commits only its reports. The PR reads as a log of real changes rather than a bare pointer at commit history.

The workflow is split by token permissions. Its `build` job runs everything above with a read-only token and commits locally, then hands its new commits to the `publish` job as a git bundle (`origin/ingest..HEAD`, which keeps the merge of `dev` intact). `publish` holds `contents: write` and `pull-requests: write` but runs only git and `gh`: it pushes the bundle to `ingest` fast-forward only, so commits pushed to `ingest` while `build` ran are never overwritten, maintains the PR, and fails the run after pushing an orphan queue. The same rule holds across CI: no job that installs or runs project or third-party code holds a write token. The Test workflow is read-only throughout, so its ingest check on `dev` fails rather than committing, and `release.yaml` builds in a read-only job, publishes the built files to PyPI from a job holding only `id-token: write`, then creates the GitHub release from one holding only `contents: write`. Release runs on every push to `main`, and `main` isn't tested again after a merge: its ruleset admits only a PR whose tests passed against an up-to-date `main`, so the merged tree is the one tested. Release tags (`v*`) can't be moved or deleted once created, under the `release-tags` ruleset.

Every workflow installs uv 0.12.19, verified against its published checksum, and the release build resolves hatchling and its dependencies only from `.github/build-constraints.txt`, by hash (`uv build --build-constraints … --require-hashes`). Dependabot doesn't update either. To move uv, change `version` and `checksum` together in every workflow, taking the checksum from the release's `uv-x86_64-unknown-linux-gnu.tar.gz.sha256`. To refresh the build constraints, rerun the command in the file's header with `--exclude-newer` moved to a week before today, which keeps the same one-week delay as Dependabot's cooldown. Dependabot's action updates target `dev` (`target-branch` in `.github/dependabot.yml`), so they're tested against the pinned workflows and reach `main` through a release like any other change. Its security updates ignore that setting and always open against the default branch, `main`, whose workflows can lag `dev`'s; close one and apply the same bump on `dev` instead (`uv lock --upgrade-package <name>`), which keeps changes flowing one way and closes the alert once the release merges.

A clean run regenerates `tests/analysis/data_stats.json` and fills the docs' stat markers from it (see Performance Profile) right after promotion, so the record counts and resolution breakdown in the README and `methodology.md` always describe the data being committed; the test suite's `render_docs.check()` fails a run whose docs don't. Timing and memory figures aren't regenerated in CI, since they depend on the host: after a change that could move them, run the whole suite with `poe analysis --notes "what changed"`, which runs the data stats, footprint and benchmarks and then fills the markers. `poe analysis --check` only checks that the docs' deterministic markers are current.

#### Source manifests

Each stage's `ingest/<stage>/inputs/*.manifest.json` records every source file its shipped data was built from, as `{url, etag, sha256}`, keyed by its local file name (a zip's extracted file, whose SHA-256 it records). The three do different jobs: the URL and ETag only decide whether to re-download, a changed URL counting as a changed source, the SHA-256 is the provenance, identifying the exact bytes a release was built from whatever the server does with its ETags, and whether a release changed anything is decided by the shipped data's diff (see Automated ingest pipeline above), not by the manifests. A run stages each manifest as it fetches, holding that run's entries alone, and promotion moves the staged manifests into place, so they always describe the shipped data and a source no longer used leaves no stale entry. The decisions a build applied need no manifest entry: `resolution_map.json` is committed alongside the data. Wikidata queries have no ETag, so each goes through a `CommittedQuery` (`ingest/utils/committed_query.py`): `CROSSWALK` for subdivisions and `COUNTRY_NAMES` for countries. Its `fetch()` runs the query on every run and stages the result, `log_changes()` logs how it differs from the committed `<name>.json`, and promotion moves the staged result into place like any other staged file. The skill reads the crosswalk's staged result through `CROSSWALK.latest()` for `wikidata_seen`, so a decision records the mapping it was actually shown. `fetch()`'s HEAD and download and `sparql()`'s queries all go through `_retrying()`, which retries a 429, a 5xx, a dropped connection or timeout, or a cut-off body up to `REQUEST_ATTEMPTS` times in all, with doubling backoff. `_download()` raises on a body shorter than its `Content-Length`, since `http.client` doesn't, so a truncated file is retried rather than recorded. `sparql()` uses POST, since the query service caches GET responses. A result missing committed keys is queried again until two in a row are missing the same keys, within `CONFIRM_QUERIES`, and the confirmed removals are logged by key for the ingest PR; the rest of the result needn't repeat, since the query service's servers lag by different amounts. iso-codes and CLDR files are fetched at their `main` branch's current commit rather than by branch name, so a manifest's URL fetches the exact bytes it records; for iso-codes, `main` rather than a release, since its releases lag well behind the ISO changes `main` takes. `iso_codes_url()` and `cldr_url()` look the commit up through salsa's and GitHub's branches APIs once per run, so every stage builds from the same commit of each.

## Registries

Every registry extends `Registry` (`src/localis/registries/registry.py`), which loads a dataset and its lookup index lazily and provides `get()`, `lookup()`, iteration and `len()`. `QueryableRegistry` extends it with the filter and search indexes and `filter()`/`search()`, and currencies, scripts, languages, countries, subdivisions and cities extend that; macroregions, a small lookup table, extend `Registry` directly and ship no filter or search index. Each registry pairs an entity (`localis/entities/`), a columnar store (`localis/stores/`) and a view that reads a row from the store and builds the entity (`localis/views/`). A view builds a new entity on every call, its nested records and collections as new lists, and copies the two things the store would otherwise share, a record's alias tuple and a country's `HistoricInfo`, so a caller changing what it got back can never change the store or a later result. Entities stay hashable despite being mutable: `Entity.__hash__` hashes the type and `id`, which agrees with the field-by-field `==`, and every entity class is declared with `@entity`, which applies `dataclass(slots=True)` and then restores that hash, since `@dataclass` removes `__hash__` from a mutable class it decorates. A view resolves references to other datasets through their views, so a registry's dataset loads the datasets it references first (languages take scripts, countries take macroregions, currencies, languages and scripts, subdivisions take countries, cities take both). On the pipeline side, a stage under `ingest/<stage>/` fetches, builds and stages its dataset with `dump_registry()` and the indexes it ships, and `run_pipeline()` runs the stages in dependency order, passing each stage's models to the stages that store its ids, then promotes the build (see Pipeline). A dataset's TSV holds one row per record with no id column, since the views number rows from 1, so no stage assigns ids: `dump_registry()` numbers a registry's records by row just before writing them, and a registry that references another reads ids that registry's earlier dump numbered. Its columns are the model's fields in order, minus its `UNSHIPPED_FIELDS` (`Model.row_fields()`, which `load_countries()` also reads the staged countries by). Each view's `load()` unpacks those columns by position, and `tests/unit/test_row_formats.py` holds the two together: it writes a model with a distinct value in every field through `dump_data()` and reads it back through the view, so a column the two order differently fails. Rows are written unquoted for the views' `split("\t")`, so the dump raises on a value holding a tab or line break, and `join_cell()` on one holding `|`, the separator of multi-value cells; `dump_lookup_index()` raises on a lookup key more than one record holds, logging each one with its records.

## Performance Profile

Every current figure in this section and in the README's Performance section is generated, never transcribed by hand; the historical comparisons (the hashid load times, the earlier memory methodologies, and what past memory work saved) are quoted as they were measured. `tests/analysis/data_stats.py` produces the deterministic numbers (record counts, the subdivision resolution breakdown, the committed Wikidata crosswalk against what shipped, shipped file sizes) into `data_stats.json`, and asserts that they reconcile. A count only the ingest can see, such as the cities that took GeoNames' ASCII name, is written by its stage to `ingest/<domain>/outputs/ingest_stats.json` for `data_stats.py` to read. `tests/analysis/footprint.py` measures load time and allocated memory per registry component, each scenario in fresh subprocesses with the median kept, and `tests/analysis/benchmarks.py` measures search's per-call latency percentiles and accuracy (`get`, `lookup` and `filter` are index reads too fast to be worth timing), where a result whose names include the unmangled query (for a city, its name with its admin1) counts as a hit like the sampled record itself, since no search can tell the two apart, and such hits are counted apart as `twin_hits`; both append to a history (`footprint.json`, `benchmarks.json`) with a fingerprint of the host they ran on. `tests/analysis/render_docs.py` fills each `<stat key="source.key:format">` tag in the docs from those files, and `render_docs.check()`, run by the test suite, fails if a deterministic marker is stale or its source file is missing. Current figures were measured on <stat key="footprint.host.cpu:raw">11th Gen Intel(R) Core(TM) i7-1165G7 @ 2.80GHz</stat> with Python <stat key="footprint.host.python:raw">3.14.7</stat>. Memory figures are the bytes a load leaves allocated, traced with `tracemalloc` after an explicit `gc.collect()`, measured in separate processes from load time since tracing slows loading; see Memory measurement methodology below for why.

### Search and filter index architecture

Both indexes keep their postings in `array.array("I", ...)` (packed 4-byte unsigned ints) rather than `list[int]`, where each id was a full boxed Python object of about 36 bytes: the cost was in the container, not the data. Both are inverted at ingest by `_dump_inverted_index()` (`ingest/utils/index.py`), which writes every key's posting list packed little-endian and concatenated in key order (`<index>.bin.gz`), byte-swapped on load on a big-endian machine, and, per key, its columns with the list's offset and count (`<index>_offsets.tsv`); a search key is a trigram and a filter key a field and value. Loading, through `read_inverted_index()` (`localis/indexes/inverted_index.py`), reads the postings in one pass and slices each list out, rather than building the reverse index from per-record rows. In the filter index a value held by a single record, which is most of them (<stat key="data.filter_index.cities.single_record_values:int">216,712</stat> of cities' <stat key="data.filter_index.cities.values:int">277,273</stat>), keeps its id as a plain int instead of a whole array. A record with no value in a field is indexed under that field's `MISSING_KEY` (`"MISSING"`, uppercase so no normalized query can equal it), which `filter(field=localis.MISSING)` looks up, since `None` already means "don't filter on this field".

Search ships two trigram indexes per queryable registry, plus a short-name list, all written at ingest by `dump_search_index` (`ingest/utils/index.py`) from the model's `CANON_FIELDS` and `CONTEXT_FIELDS`. The canon index holds the trigrams of the fields naming a record (its name, official and common names, aliases and ISO suffix) and the context index those of the fields locating it (its parent, admin1 and country); each is a gzipped blob of every trigram's sorted ids packed as uint32 (`canon_index.bin.gz`) with an offsets table (`canon_index_offsets.tsv`, plain text so it stays git-diffable). Loading decompresses each blob and `array.frombytes()`s it in one bulk call, then slices per-trigram arrays out of it using the offsets, decode once and slice many. Each also ships `short_names.tsv.gz`, every one-word canon name of at most 7 normalized characters with its record id, for the short-query fallback below. Cities were left out at first, since their queries usually carry context, until an exact search for a four-letter city (Jīān) failed: it shares all its trigrams with dozens of longer names and missed the shortlist. Theirs adds <stat key="data.shipped_size.cities.files.short_names.tsv.gz:size">473KB</stat>. Trigrams are built by `word_trigrams()` in `localis/utils/strings.py`, shared by ingest (through `search_trigrams()`, which normalizes raw field text first) and runtime (on the query's already-normalized tokens) so the index and the query can't drift apart: text goes through `search_text()` (`normalize()`'s form with punctuation turned into spaces; `normalize()` casefolds, strips accents from Latin letters and spells out from `LATIN_FOLDS` the Latin letters Unicode decomposition leaves alone, and leaves other scripts as written, though every shipped name is Latin), and each word is padded with two leading spaces and one trailing one, so a short word keeps its edge trigrams through a typo. The registries own the search policy: each lists its `NAME_FIELDS`, the view fields fuzzy-matched as names, so tuning scoring never needs a re-ingest.

A query runs in three stages in `SearchIndex.search()`. Each query trigram first gets a rarity weight, `log(records / records containing it)` from its posting lengths, so a trigram in tens of thousands of records counts for almost nothing and a distinctive one for a lot. Stage 1 counts, per record, the query trigrams in its canon and context together with `Counter.update()`, which counts a whole id array in C; trigrams in more than 2% of records (and more than 1,000) are skipped as long as 3 rarer ones remain, since they are the longest lists to count and the least telling, such as a country name's trigrams in the context of every city in it. The 200 records with the most hits, or `limit` if larger, form the shortlist. Stage 2 computes each shortlisted record's exact rarity-weighted coverage of the query by binary search on the sorted postings, each trigram counted once with canon taking priority over context, and scores it as the mean of its canon coverage and its canon and context coverage together; a record with no canon coverage is dropped, so context alone never surfaces a record, and the top 50, or `limit` if larger, go on. A one-word query of 6 characters or fewer also takes, from the shipped short names within one character of its length, the closest by `rapidfuzz` `ratio`, since a short word with a typo shares only common edge trigrams with its record and would never survive stages 1 and 2. Stage 3 scores each candidate's names: for every name and every span of the query with the name's word count, `token_sort_ratio`, or plain `ratio` when either side has several words and a typo has changed the sorted word order, gives the name score, which is reduced by up to half by the rarity-weighted share of the rest of the query missing from the record's context trigrams, and the candidate keeps its best name and span. Results under 0.5 are dropped, and ties are broken by the stage 2 score.

### Subdivision hashid

`SubdivisionModel.hashid` is an MD5-derived id used only during ingestion (merging ISO and GeoNames records, and supporting the resolve-subdivisions skill). It used to be computed in `__post_init__`, which runs on every construction, including the normal runtime `_cache` load, where nothing ever reads `hashid`, it's discarded once a subdivision has been merged. `set_hashid()` is now an explicit method, called only at the two ingestion sites that actually need it (`ingest/subdivisions/scripts/geonames_subdivisions.py`, `ingest/subdivisions/scripts/iso_subdivisions.py`); the runtime reads subdivisions through `SubdivisionView` and never builds a `SubdivisionModel`. Subdivisions' dataset load dropped from 289.5ms to 98.7ms (−66%) as a result.

### Memory measurement methodology

Earlier benchmarks in this document used `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss`, the process's historical peak resident memory, which only ever increases and never reflects memory freed later in the same process. That overstates any component whose loading path allocates a large transient buffer it doesn't keep: A `SearchIndex` decompresses its entire gzip blob into one big `array("I")` before slicing per-trigram arrays out of it (a copy, not a view), so the decompression peak gets permanently recorded by `ru_maxrss` even after that buffer is freed and unmapped moments later. Re-measuring with actual post-GC retained memory (`VmRSS` after `gc.collect()`) showed cities' search index really retains about a third of its previously documented figure (35.1MB vs. 101.5MB), while cache and filter index numbers, which don't have this transient-buffer pattern, held up closely under both methodologies. That retained figure was itself the change in `VmRSS` around each load, which undercounted any component loaded after another: the allocator reuses memory an earlier load freed without growing the process, so the cities lookup index, loaded after the dataset parse, showed 4KB against a 3.4MB index file. Memory is now traced with `tracemalloc`, the bytes still allocated through Python's allocators once a load finishes and garbage is collected, which doesn't depend on what loaded before. It counts the bytes requested, not the allocator's own overhead, so it reads somewhat below resident memory. All numbers below use the traced methodology.

### Population floor

`CityRegistry.set_population_threshold(n)` narrows the cache and all three indexes to cities with population >= n, raising right away for a threshold that isn't a non-negative int. It sets the registry's row filter, a `CacheFilterPredicate` (`row -> bool`, in `localis/utils/data.py`) built by `CityView.population_filter()`, next to the row layout it reads, and evaluated by `CityView.load()` as it parses each TSV row, since population is only known once that row is parsed. The indexes have no population data of their own, so they're narrowed by id instead: `Registry._allowed_ids` is the set of ids the filtered cache kept, or `None` when no row filter is set, and `FilterIndex`, `SearchIndex` and `LookupIndex` load only those ids. `_allowed_ids` is cached and derived from the cache itself, so it always matches the cache it came from, and setting a new threshold invalidates both under the registry's lock, while setting the one already in place keeps them.

Ids stay stable across thresholds. `Store.id_to_idx` (an `array.array("i")` sized to the full unfiltered id space, `-1` for an excluded id) decouples a View's physical position in its Store from its public `id`, so `View._idx` resolves through this array instead of assuming `id - 1`. That lets `CityStore` skip allocating rows for excluded cities entirely, a real memory saving rather than just fewer View wrapper objects, without ever renumbering an id a caller might already be holding.

At a <stat key="data.cities.threshold:int">15,000</stat> threshold (the tier geonamescache ships as a separate bundled dataset), cities drops from <stat key="data.cities.total:int">235,970</stat> to <stat key="data.cities.above_threshold:int">34,172</stat> and memory drops from <stat key="footprint.registries.cities.combined.memory_bytes:size">126.9MB</stat> to <stat key="footprint.cities_threshold.memory_bytes:size">29.8MB</stat>.
